From a link to a library

How the schema behind a personal media library gets derived, one honest failure at a time. Nothing here is decreed. We start with the smallest thing a person can save, let real examples break the design over and over, and let each break earn exactly one new piece. By the end, every field has a story you can retell at a whiteboard.

Act one

The thing you saved

Before we can understand content, we have to be able to hold it. Act one is about the container: identity, time, ownership, and multiplicity.

Step 1

Start with a link

"Save this for later." The smallest schema that keeps the promise is one field:

{ "url": "https://www.tiktok.com/@bhaihours/video/752102..." }

For a bookmark manager circa 2005, we are done. Everything that follows is what happens when you take the promise seriously: later might be years away, the thing might be gone by then, and "this" turns out to be a slippery word.

Step 2

The thing with no address

What breaks it: you drag a screenshot in from your camera roll. It has no URL. Nothing ever gave it one.

If url is required, an honest piece of content gets rejected at the door. And once you see it, you see the deeper mistake: a URL was never the identity of anything. It was one kind of handle. A TikTok also has a platform ID that outlives URL changes. A local file has only its bytes, and bytes can be fingerprinted: run them through a hash function and the same file always produces the same short string.

{ "identity": {
    "status": "platform_verified | inferred | synthetic",
    "permalink":   "https://...",        // when one exists
    "canonicalId": "7521027298...",      // the platform's own ID
    "contentHash": "sha-256:9f2ab..."    // the bytes themselves
} }                                     // at least one handle, any kind
Rule 1Never require a field that some real thing cannot supply. Only two facts are universal: the thing exists, and you saved it at some moment.
Step 3

Links rot

What breaks it: you click a saved link two years later. Paywall. Or the article was edited. Or the account is gone and the page is a 404.

What you saved and what is out there stopped being the same thing the moment you saved it. So the library stores its own copy where it can, records when it looked, and admits how much it actually got. A paywalled article where we only captured the headline should say so, on the record, forever. And the live thing keeps its own status, checked over time: still up, changed, delisted, dead.

{ "identity": { ... },
  "assets": [ { "blobRef": "...", "contentHash": "..." } ],   // our copy
  "capturedAt": "2026-07-06T20:14Z",
  "captureFidelity": { "level": "full | partial | metadata_only",
                       "gate": "none | paywall | login | drm" },
  "lifecycle": { "state": "live | changed | delisted | dead",
                 "lastCheckedAt": "..." } }
createdAt

(their clock)
savedAt

(your clock)
capturedAt

(our clock)
lastCheckedAt

Four different moments. Collapsing them into one "date" field is how libraries quietly lie.
Rule 2A save is an observation of the world at a moment. Observations carry timestamps, and different clocks never share a field.
Step 4

You are part of the data

What breaks it: which folder you filed it in. The note you wrote on it. The fact that you favorited it on Tuesday and liked it again on Friday.

None of those are facts about the video. They are facts about you and the video. Mix them into one object and you can never share a record, dedupe a record, or answer "when did I save this" separately from "when was this made." So the object splits in two. Libraries solved this centuries ago: the book is one thing, the catalog card that says where it sits and who checked it out is another.

{ "save": {                                // yours
    "sources": [ { "kind": "favorites", "at": "Tue" },
                 { "kind": "likes",     "at": "Fri" } ],
    "collections": ["food"], "note": "..." },
  "post": {                                // the world's
    "identity": { ... }, "capturedAt": ..., "lifecycle": ... } }
Rule 3Facts about the world and facts about you live in different objects.
Step 5

One episode, two apps

What breaks it: the same podcast episode exists on Spotify and on Apple Podcasts. Two pages, two platform IDs. One episode.

Save both and a naive library counts two unrelated things. The fix is a third level above the post: the work itself. And here the world helps us, because it already maintains identities at this level. Podcast feeds carry a shared GUID by spec. Papers have DOIs. Books have ISBNs. Recordings have ISRCs. When such an identifier exists, we record it, and the two posts join.

{ "post": {
    "workRef": { "scheme": "podcast_guid | doi | isbn | isrc",
                 "id": "..." },   // same on Spotify + Apple
    ... } }
Workthe episode itself · "Ep. 214" · one podcast GUID
▲ appears as
Postits appearance on Spotify · its appearance on Apple
▲ kept by
Saveyour act of keeping it · folder, note, moment
Librarians formalized this ladder in the 1990s (they call it FRBR). We walked into it backwards, which is a good sign.
Rule 4Reuse identities the world already maintains before minting your own.
Step 6

One save, many things

What breaks it: an Instagram carousel. Twelve images, one permalink. Or you save a thread: thirty-nine posts you want kept as one item.

A flat object cannot hold an ordered list of other objects. And there is a subtle cousin hiding here: a playlist also holds many things, but differently. The carousel's slides belong to it and have no life of their own. A playlist merely points at songs that exist independently. Two relationships, so two fields, and the save itself records its scope: did you mean the one post, or the whole thread it sits in?

{ "post": {
    "children":   [ { "order": 1, "post": {...} }, ... ],   // parts of it
    "membership": [ { "container": "...", "order": 7 } ],   // listed in
    ... },
  "save": {
    "scope": { "kind": "post | thread | container",
               "members": ["...", "..."] },
    ... } }
Rule 5Containment and curation are different relationships. One field cannot hold both.
Step 7

A photo of a tweet

What breaks it: you screenshot a tweet and save the image.

What you saved is a photo. What you meant is the tweet, which has an author, a claim, and a life of its own. Treat the screenshot as a mere image and the same tweet saved natively and saved by screenshot count as strangers. So a post can declare that it depicts another thing, as an inference, with a confidence attached, and the link can chain: a screenshot of a quote-tweet of a TikTok is three layers, each recorded.

{ "post": { "mediaKind": "photo",
    "references": [ { "rel": "depicts",
        "target": { "platform": "x", "identity": { "status": "inferred" } },
        "confidence": 0.86 } ],
    ... } }
what you saved: a photo (has a content hash, no permalink)
what it depicts: a tweet (inferred, confidence 0.86)
what the tweet quotes: a TikTok (chain continues)
Dedup and search land on the innermost thing you meant. The outer photo is still kept, untouched.
Rule 6Model what the user meant without losing what they actually saved.
Act two

What the thing means

The container is sound. Now the harder half: a library you can search by meaning has to know what each item says, shows, and refers to. This is where most tools wave their hands. We will not.

Step 8

Six doors

What breaks it: "what does this TikTok say?" is really several questions wearing one coat.

A voice says one thing. The caption says another. Text burned into the frames says a third. The pictures themselves show something, the song sets a mood, and the platform attaches its own labels. Mash them into one text blob and you can never again ask "was that said out loud, or written on screen?" So content arrives through named doors, and we chose the names by how a person perceives, not by what a platform ships. That choice is what lets a TikTok and a Reddit post live in one library: the Reddit post simply has fewer doors open.

VERBAL_AUDIOspoken words: narration, dialogue
VERBAL_TEXTwritten words: caption, body, title
VISUAL_TEXTtext inside the frames: overlays, signs
VISUAL_SCENEthe imagery itself: places, objects, faces
NONVERBAL_AUDIOmusic and sound that is not speech
STRUCTURED_METADATAplatform fields: hashtags, music tag, subreddit
Six doors, fixed forever. A new platform opens some and leaves others shut. The list never grows per platform.
"signals": [
  { "id": "audio",   "channel": "VERBAL_AUDIO" },
  { "id": "caption", "channel": "VERBAL_TEXT" },
  { "id": "frames",  "channel": "VISUAL_SCENE" } ]
Rule 7Describe content by human perception, not platform feature. Perception is what survives the next platform.
Step 9

Manufactured witnesses

What breaks it: "the transcript" sounds like a fact about the video. It is a machine's guess at the audio.

Speech recognition mishears names. Text recognition misreads stylized fonts. These manufactured signals are enormously useful and quietly fallible, so each one records what it was made from and by what. When a name looks misspelled you can then ask the right question: did the creator misspeak, or did the transcriber mishear? Each signal also carries its language, and a translation is simply one more manufactured signal pointing back at its source.

"signals": [
  { "id": "audio",      "channel": "VERBAL_AUDIO" },
  { "id": "transcript", "channel": "VERBAL_TEXT",
    "producer": "asr:whisper-v3", "wasDerivedFrom": "audio",
    "language": "ko" },
  { "id": "transcript-en", "wasDerivedFrom": "transcript",
    "producer": "translation:...", "language": "en" } ]
Rule 8When a witness is manufactured from another, keep the manufacturing record.
Step 10

Which Joe's?

What breaks it: a video praises a restaurant called Yoo Yee. Next month you search "that Cantonese place." The strings do not match. You did not save a spelling; you saved a place.

For the library to connect them, "Yoo Yee" has to stop being text and become a thing: the restaurant, with a public identifier that the rest of the world also uses. A Google place ID. A MusicBrainz recording ID for a song. A Wikidata number for a film. This step, called grounding, is where two hard rules were earned the painful way.

First: the language model never writes the identifier. Ask a model for an ID and it produces something plausible, and a plausible wrong ID poisons a library silently. The model may only say "a song called X by artist Y plays here." Ordinary, boring code then searches the registry and finds the match, or does not.

Second: "no match" is an answer, and a good one. From our own corpus: the song "jazz is for ordinary people" by berlioz resolves to a real MusicBrainz recording. The audio labeled "original sound - sunny" resolves to nothing, because TikTok original sounds have no global registry, and the correct record says exactly that instead of inventing one.

"extractions": [
  { "role": "named_entity",
    "referent": { "kind": "place", "surface": "Yoo Yee" },
    "grounding": { "authority": "google_places",
                   "externalId": "ChIJ...", "confidence": 0.91 } },
  { "role": "named_entity",
    "referent": { "kind": "music_recording",
                  "surface": "original sound - sunny" },
    "grounding": { "authority": "musicbrainz",
                   "externalId": null,          // honest
                   "nil": "no_match_exists" } } ]
Rule 9The model never writes the ID, and an honest "no match" outranks a confident wrong answer.
Step 11

Ideas have no address

What breaks it: the same video is also about sourdough hydration. No registry hands out IDs for ideas with pins on a map.

Yet "about sourdough hydration" is exactly what you will search for. The test that separates the cases: could there be many of it? Yoo Yee names one specific place, an instance. Sourdough hydration names a kind of thing, a concept. Concepts resolve against subject vocabularies instead of registries (Wikipedia's concept entries, the news industry's topic lists), and near misses earn partial credit: tagging "bread baking" when the truth is "sourdough hydration" is close, and the grading knows it. For an instance, close does not exist. You either found the right restaurant or you did not.

Rule 10Things and ideas ground differently. Forcing one machinery onto both breaks both.
Step 12

"Worth the hype"

What breaks it: the caption says Yoo Yee is worth every bit of the hype. That is not a thing and not an idea. It is a claim.

You cannot look a claim up anywhere. The only fair questions are: did the video actually assert this, and did we capture the assertion faithfully? So claims are stored as propositions, linked to the things and ideas they are about, and graded on faithfulness to the source. Note what the library refuses to do: it certifies "this video said this." It never certifies "this is true." Deciding truth is a fact-checker's job, and a tag generator that pretends otherwise is a misinformation machine with a nice interface.

{ "role": "claim",
  "referent": { "text": "Yoo Yee lives up to its hype",
                "predicate": "recommends",
                "about": ["#the-yoo-yee-entity"] },
  "grounding": null }                // by design: graded on faithfulness, never linked
Rule 11Record assertions as assertions. Grade faithfulness to the source, never truth about the world.
Step 13

Content with a shape

What breaks it: a recipe video. "About pasta" is true and useless. The value is in the parts: ingredients, quantities, steps in order.

Some content has a known shape, and when it does, the shape is worth more than any summary. So the schema recognizes templates (a recipe, a workout, a ranked list, a how-to) and fills their slots, with each slot pointing back down at the layers below: an ingredient is a food concept, a mentioned brand of pan is an entity. Capture the shape and "what can I cook from what's in my fridge" becomes a query instead of a wish.

{ "role": "structured_content",
  "shell": "Recipe",
  "slots": { "ingredients": [ { "concept": "#brown-butter", "qty": "3 tbsp",
                                "observedAt": "..." } ],
             "steps": [ "...", "..." ] } }
Rule 12When content has a known shape, capture the shape, not just a summary of it.
Step 14

Same subject, different creature

What breaks it: two videos about knee pain. One is a physiotherapist's careful tutorial. The other is a comedian's skit.

Identical subject, opposite nature, and "about knee pain" describes both. What separates them is not another subject but a different kind of descriptor: genre, intent, mood, who is speaking. Each of these is an independent dial with a small fixed set of values, and the dials combine freely. The tempting alternative, one big tree of categories, explodes on contact: you would need a branch for funny tutorials about health by professionals, and then another for every other combination. A librarian in 1930s India, S. R. Ranganathan, worked this out for physical libraries. Independent dials multiply cleanly; trees do not.

"facets": { "genre": "tutorial",   // or: skit, review, haul...
            "intent": "teach",     // or: sell, entertain, vent...
            "affect": "calm",
            "creatorRole": "professional" }
Rule 13Independent descriptors stay independent. Dials, never one giant tree.
Act three

Proof

Acts one and two produce descriptions. Act three is what makes them trustworthy, which is the difference between a library and a rumor mill.

Step 15

No claim without a receipt

What breaks it: the machine says this video mentions Nike. Says who? Based on what?

If you cannot ask, you cannot trust, and an untrusted library is decoration. So every extraction, whether entity, concept, claim, or facet, must carry evidence: which signal it came from, where exactly inside it (a quoted phrase, a time range, a region of a frame), and how it knew. Said out loud, shown on screen, reported secondhand, or inferred from context. Evidence is plural because arrival is plural: the swoosh in frame two and the word in the caption are two receipts for one entity, each with its own confidence. And it is required. An extraction arriving with zero receipts is rejected as a bug.

One requirement, three payoffs. The user can see why the library believes something. The accuracy becomes measurable, since receipts can be graded against a human-labeled answer key. And uncertainty becomes honest: inferred is labeled inferred, and scores can be reported separately for said versus guessed.

"signal": "caption"
where it came from · which door
"selector": { "quote": "Yoo Yee" }
where exactly · a span, a time range, a frame region
"assertionMode": "STATED"
how it knew · stated, shown, reported, inferred
"confidence": 0.98
how sure · calibrated, not decorative
"extractor": "engine@1.4.0"
who says so · model and version, for the audit trail
Anatomy of one receipt. Every extracted fact carries at least one.
Rule 14An extraction without evidence is a bug, not a row.
Step 16

The whole record

Here is the Yoo Yee video, a real item from a real 4,661-item corpus, assembled. Every field below was earned by one of the fifteen steps above.

{ "save":  { "sources": [{"kind":"favorites","at":"..."},{"kind":"likes","at":"..."}],
             "scope": { "kind": "post" } },
  "post":  { "identity": { "status": "platform_verified", "canonicalId": "7643844...",
                           "permalink": "https://tiktok.com/..." },
             "creator": "@...", "mediaKind": "video",
             "body": "Yoo Yee is worth every bit of the hype...",
             "assets": [ { "blobRef": "poster", "contentHash": "..." } ],
             "capturedAt": "...", "captureFidelity": { "level": "full" },
             "lifecycle": { "state": "live", "lastCheckedAt": "..." } },
  "signals": [ "caption", "audio", "transcript ⇠ audio", "frames", "metadata" ],
  "extractions": [
    entity   "Yoo Yee" → google_places ChIJ...        (caption STATED + frames SHOWN),
    entity   "Coffee & Vinyl - Emi Izumi" → NIL       (metadata STATED),
    concept  "Cantonese cuisine" → wikidata Q...      (transcript INFERRED),
    claim    "lives up to its hype" → faithfulness    (caption STATED),
    facets   genre: review · intent: persuade         (whole item) ] }

Three meta-rules keep the object alive for the next decade rather than the next sprint.

Grow by adding. A field, once shipped, never changes meaning. Retired fields are marked deprecated and kept, because thousands of stored items cannot be re-asked. Everything in this derivation was additive for exactly this reason.

One base, many profiles. Every platform is an adapter plus a small profile of platform-only extras. The base object never changes when a platform is added, and the test is mechanical: every item, from a TikTok to a screenshot to a PDF, validates against the same base shape. That single check is what makes "show me every restaurant I ever saved, from any app" a query rather than a feature request.

Grade each layer with its own ruler. Entity IDs are right or wrong. Concepts earn partial credit. Claims are graded on faithfulness, facets on plain classification accuracy. Averaging those into one number would be statistically meaningless, so the published scorecard is a small table, one honest metric per layer, with "no match" rates shown rather than hidden.

Rule 15Grow by addition. Validate everything against one base. Grade each kind of meaning on its own terms.
Epilogue

What writing this exposed

Deriving a design in public doubles as a review of it. Four things surfaced during the writing.

Language was missing. Nothing recorded that a transcript is in Korean, or that a translation exists. Signals now carry a language tag, and a translation is just another manufactured signal under rule 8. No new machinery.

Save timestamps were too coarse. "Favorited Tuesday, liked Friday" is two moments, and the old shape kept one. Each source on a save now carries its own time.

Volatile values wanted one pattern. A price, a like count, and a "still alive?" check are the same species: a value plus the moment we observed it. One observation pattern now covers all of them instead of three ad hoc fields, and re-observing simply appends.

Your own notes need nothing new. A note you write yourself is a post whose creator is you and whose only open door is written words. The schema absorbed it without an edit. When a case you never designed for fits without change, the derivation is doing its job.

The old name for a book like this library is a commonplace book: collected fragments, indexed by subject, annotated in the margins, kept for reuse. Every field above exists to keep that old promise, with receipts.

The fifteen rules, in one place

  1. Never require a field that some real thing cannot supply.
  2. A save is an observation; observations carry timestamps, and different clocks never share a field.
  3. Facts about the world and facts about you live in different objects.
  4. Reuse identities the world already maintains before minting your own.
  5. Containment and curation are different relationships.
  6. Model what the user meant without losing what they actually saved.
  7. Describe content by human perception, not platform feature.
  8. When a witness is manufactured from another, keep the manufacturing record.
  9. The model never writes the ID; an honest "no match" outranks a confident wrong answer.
  10. Things and ideas ground differently.
  11. Record assertions as assertions; grade faithfulness, never truth.
  12. When content has a known shape, capture the shape.
  13. Independent descriptors stay independent.
  14. An extraction without evidence is a bug, not a row.
  15. Grow by addition; one base, many profiles; grade each layer on its own terms.
